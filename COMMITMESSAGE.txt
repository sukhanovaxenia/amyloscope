1. MULTIPLE COMPARISONS
================================================================================

  src/amyloscope/analysis/multiple.py   (new)

    benjamini_hochberg()   step-up FDR control (BH 1995)
    holm()                 step-down FWER control
    n_discoveries()

Validated against scipy.stats.false_discovery_control over 300 random families,
agreeing to 2.2e-16. Validated against the library rather than against values
written down from memory: a hand-copied expected column is exactly as likely to
be wrong as the code it checks, and the first draft of this message quoted a
reference value that was wrong while the implementation was right.

NaNs pass through without entering the denominator. A test that could not be run
is not a test that failed to reject, and counting it in m penalises every other
test in the family for a comparison that never happened.

BH rather than Holm for the per-protein family: the question there is "which of
these proteins show the effect", and controlling the false discovery rate is the
right error to control for a screen of a few hundred. Holm is provided for the
smaller families -- a handful of ranks, a handful of domains -- where a
family-wise rate is the right choice and the power cost is affordable. A test
pins that Holm is never less conservative than BH, since if it ever looked
cheaper something would be badly wrong.


  src/amyloscope/analysis/termini.py

    ProteinTerminalBias.q_position    BH-adjusted p, per protein
    TerminalBiasResult.fdr_alpha      the threshold the counts are reported at
    TerminalBiasResult.n_significant  proteins significant AFTER adjustment
    TerminalBiasResult.n_directional  proteins with a usable direction
    TerminalBiasResult.sign_test_p    exact binomial test on the directions
    per_protein_p_floor               the smallest p this design can produce

The adjustment changes what the analysis can claim, and the interesting part is
that it does not weaken the result -- it separates two results that were being
reported as one.

On the FXR1 set:

    direction      91 of 91 proteins shift N-terminal
                   sign test p = 8.1e-28
    individually   0 of 91 proteins significant at FDR 0.05

Both are true and they answer different questions. Each protein carries about
four APRs, so the smallest p a per-protein permutation test can return is
bounded well above any FDR threshold -- the per-protein family can be entirely
null while the pooled direction is unanimous. That is a statement about the
power of a four-observation test, not about the biology.

What would have been wrong is either half alone. Reporting 91/91 and an
unadjusted per-protein table invites "and 37 of them are individually
significant", which multiplicity would have removed. Reporting only the adjusted
count invites "no protein shows the effect", which the unanimous direction
contradicts. format_terminal_report() now leads with DIRECTION and then
INDIVIDUALLY, in that order, and states the p-floor so a reader can see why the
second number is zero.

The direction test is a sign test on the directions rather than anything
fancier, because that is the question: the pooled shift could be driven by a few
proteins with large effects, and the sign test asks whether the effect is
general. 91/91 says it is.

2. FIGURE LABELS
================================================================================

  src/amyloscope/io/metadata.py   (new)
  src/amyloscope/config.py        labels: section, applied at load

ProteinSpec.display_name is already the single place a figure's axis label comes
from, and for a handful of proteins the config carries the names directly. For a
sweep that does not work: 372 accessions cannot be hand-named, and an axis of
accessions makes the reader do a lookup for every row. So a metadata table
supplies them -- one row per protein, an `id` column matching the protein ids,
and the label built as a template over the table's other columns.

  labels:
    table: meta.tsv              # relative to the config file
    template: "{tax_name} {group}"
    id_column: id
    require_all: false

This is a choice, not a formatting detail, so the policy is written down:

  1. LABEL BY MEANING. Default "{tax_name} {group}" -- what a reader of a
     comparative figure is actually comparing.

  2. FALL BACK DOWN A CHAIN so a partly resolved table still labels every row:
     the full template, then species, then group, then the bare id. A row with
     no metadata gets its accession, never a blank or a guess.

  3. DISAMBIGUATE COLLISIONS WITH THE ACCESSION, ON EVERY MEMBER OF THE SET. A
     suffix on one row of a colliding pair reads as a correction applied to that
     row; on both it reads as a property of the pair, which is what it is. The
     accession rather than the full id, because inside a colliding set the
     taxon is identical by construction, so the taxid prefix spends axis width
     saying the same thing on every member.

     This also makes a wrong template visible rather than misleading. Two FXR1
     orthologues under "{group}" are both "FXR1", and the axis then comes out
     ugly in a way that says the template is wrong for this figure -- instead of
     readable and wrong.

  4. THE ID STAYS AUTHORITATIVE. This only ever sets display_name. Every path
     lookup, join and provenance record still goes through ProteinSpec.id, so a
     figure becoming readable never costs the ability to say which sequence
     exactly a row was.

An explicit display_name in the config is never overruled: a name written by
hand is a deliberate statement, and a table should not silently replace it.

require_all refuses a partially covered set. Half an axis in species names and
half in accessions is the one outcome worse than all accessions, so it is
available as an error rather than something to notice in the figure.

Delimiters are taken from the file suffix before sniffing. A .tsv parsed as CSV
yields a single column named after the whole header line, after which every
label falls back to the id -- which looks like missing metadata rather than a
parsing mistake, so it is worth not relying on a sniff.

On the FXR1 metadata, end to end: 372 labels, all 372 distinguishable, none
falling back to a bare accession, 52 disambiguated -- those being species that
contribute several sequences to the same group, e.g. the six Acyrthosiphon pisum
pre-duplication genes.

The same policy lives in amyloevo.io.annotate, which is what builds these
tables. amyloscope is the consumer here: it does not resolve taxonomy and will
not invent a species name the table does not carry. Writing it in both places
caught a real divergence -- the suffix was the full id here and the accession
there, differing on 52 of those 372 rows -- so a test in each package now pins
the two to the same output.

3. THE `aggressor` ADAPTER, AND TWO DEFECTS IN ITS NEIGHBOURS
================================================================================

Every adapter here parses one tool's native export. This one parses the output of
aggressor-wrappers, and it exists because a config generated by that package named
`adapter: aggressor` -- which no registry entry provided, so a 372-protein handoff
could not load at all.

io/adapters.py -- parse_aggressor

  The execution layer has already done the per-tool work: it ran the predictor, read
  whatever shape that tool emits, and binarised it with that tool's own threshold
  AND direction. PASTA's pairing energy is amyloidogenic when LOW, AGGRESCAN's Hot
  Spots come from NHSA rather than from the a4v profile, WALTZ cuts on 0-100 while
  APPNN cuts on 0-1. So what crosses the boundary is the CALL, and the detection
  strategy for this adapter is `flag` on APR rather than a threshold. None of those
  rules has to be restated in an amyloscope config, and none of them can drift
  between the two packages -- which is the point of having an execution layer.

  A track WITHOUT an APR column is refused rather than scored from Score with a
  generic cut. Two reasons, and the first is quiet: a tool read that way would call
  nothing where its real calls were negative-scored, so a panel would lose a voter
  without saying so, and a fractional consensus counts voters -- every tier beneath
  it moves. The second is that a generic `>=` inverts an inverted-scale tool
  outright. The error names both the consequence and the command that fixes it.

  Boolean spelling is normalised across the ways a CSV can carry one: pandas writes
  True/False, a spreadsheet writes TRUE or 1, and a CSV has no booleans at all. A
  test covers each spelling, because a track whose APR column reads as all-false is
  indistinguishable from a tool that found nothing.

  A length disagreement between the track and the configured sequence raises with
  both counts and the likely cause -- a config built from a different FASTA, or a
  duplicate header whose later record replaced an earlier one of a different length.
  That was the failure in practice: 793 positions against a 792-residue sequence,
  surfacing as a KeyError three layers down.

  Provenance is carried where present and required nowhere: window_size and
  aggregate say how far a boundary can be trusted, coverage_depth marks the termini
  where a value rests on fewer windows, and heads_used flags an ensemble that ran
  short of its full complement.

tests/test_adapters_aggressor.py (new)

  13 tests. The ones worth naming: a track whose every Score is 0.1 while APR says
  16-21, so a generic threshold would call nothing and the test proves the call is
  read rather than derived; the same for negative PASTA-like scores, which a
  threshold would invert; and the length mismatch, asserted to name both numbers.

io/adapters.py -- the flag column, under a pandas that does not use `object`

  The boolean normalisation this message promises above was written as
  `if calls.dtype == object:`, with a numeric branch underneath. pandas 3 infers
  a `str` dtype for a text column rather than `object`, so under pandas 3 that
  test is False for an ordinary CSV of yes/no, the numeric branch runs,
  `to_numeric` coerces every value to NaN, `fillna(0)` makes it zero, and the
  track reads as a tool that called NOTHING.

  That is the failure this adapter's own docstring says it refuses to allow: a
  panel quietly missing a voter, with every fractional tier beneath it moved, and
  no error anywhere. It is also version-dependent, so it would have appeared on
  one machine and not another -- the parametrised yes/no case in
  test_adapters_aggressor.py was already failing on pandas 3.0.5 while passing on
  2.3.3.

  `_truthy()` replaces the dtype test: booleans by `is_bool_dtype`, numbers by
  `is_numeric_dtype` and `> 0.5`, everything else lowercased and matched against
  a token set shared with `core.regions._DEFAULT_TRUTHY`, so the two paths agree
  on what a flag means. Digits stored as text are still read as numbers.

io/adapters.py -- parse_appnn resolved by name

  The last adapter in this module still assigning `df.columns = [...]`
  positionally, which is the failure the module docstring says was eliminated
  everywhere else. A file with `score` and `is_hotspot` transposed yields `Score`
  holding False/True and `is_hotspot` holding 0.15/0.85; `_finalise` coerces the
  booleans to 0.0/1.0 without complaint, and a config reading
  `detection: {method: flag, column: is_hotspot}` then matches nothing.

  The hardcoded `sep="\t"` was the other half: this project's own
  appnn_converter.R writes COMMA-separated output
  (sequence_name, aminoacid_position, aminoacid, aminoacid_score, hotspot_region),
  which raised "Length mismatch: Expected axis has 1 elements" -- downgraded by
  the loader to a warning, so APPNN simply vanished from the panel rather than
  failing. `_read_table` sniffs the delimiter, as every sibling adapter does, and
  the columns are picked by name with the R converter's spellings among the
  aliases.

  Neither affected the FXR1 run, which read its tracks through the `aggressor`
  adapter rather than this one. Both are live hazards for anyone reading native
  APPNN output, and the first for anyone on pandas 3.

4. CLUSTER FIGURES PAGINATED ON THEIR OWN COUNT
================================================================================

  src/amyloscope/viz/paging.py   cluster_pages()
  src/amyloscope/pipeline.py     uses it
  tests/test_paging.py

The cluster figure draws one lane per CLUSTER, and a protein contributes however
many it has: 372 proteins produced 2,654 lanes and a 334,802-pixel image. The
first fix paginated the clusters as if the result were a list of them, which
raised `TypeError: 'ClusterResult' object is not iterable` -- it is a dataclass
holding a protein -> clusters mapping.

cluster_pages() flattens that mapping, chunks on the cluster count, and regroups
each page back by protein with dataclasses.replace, so a page is the same type
with a smaller mapping and plot_cluster_cores needs no change. Per-protein
grouping survives inside a page, so a page still reads protein by protein.

Paginating by protein instead would have been the obvious alternative and is
wrong for the same reason the original was: one page would still hold however
many clusters its proteins happen to carry.
